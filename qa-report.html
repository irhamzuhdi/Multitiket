Blocker

Flight search never resolves — "Searching flights…" forever

CGK→DPS · CGK→SUB

Searching any route hangs indefinitely on the results screen. No error, no empty state — the spinner never stops, on two independently tried routes and dates.

Root cause, from the network trace: the backend fans a search out to several vendors in parallel. One of them fails outright, and that single failure appears to take the whole result set down with it — even the vendor that answered correctly, with a real fare, never reaches the screen.

400 POST /flight/search {"errors":{"detail":"vendor error: Airline AssistCard argument not allowed. Please check your user's company setting."}} 200 POST /flight/search → Kalstar CGK→DPS, real fare, HTTP 200 200 POST /flight/search → Schedules: null 200 POST /flight/search → Schedules: [] (empty)

Two fixes, one urgent and one structural: get AssistCard's company-setting error resolved on this account, and — separately — stop letting one failed vendor call erase the others (swap whatever aggregates these calls for something that tolerates partial failure, e.g. Promise.allSettled).

Downstream impact — every suite that depends on a fresh organic search is blocked end-to-end: Hasil Pencarian, Flight Summary, Payment, Booking Confirmed, Flight Book & Payment.

Blocker

Session expires silently — no warning, just a logged-out Home page

/individual · any authed route

After roughly an hour of use, the access token lapses. Visiting a page that requires login doesn't prompt for re-auth or say anything — it silently drops back to Home with the Login button showing again, as if the session had never existed.

GET /gateway/api/v1/me → 401 Unauthorized (background, unseen by user) goto /individual → redirected to Home, Login button reappears

A traveller midway through a long form (passenger names, add-ons) gets no notice before that work is at risk. Worth a visible "your session ended — sign back in" moment rather than a silent bounce.

Resolved this session

Whole authenticated test suite was checking the wrong page

8 spec files · ~150 cases

The app routes by plain path (/my-flight-booking); the suite was navigating by hash (/#/my-flight-booking), which this router doesn't resolve on a cold load. Every one of those gotos silently rendered Home instead — and passed anyway, because the assertions were weak enough (page loaded, no login form) to pass on Home too.

Before fix "78 passed" — effectively 0 verified the intended page
After fix 75 passed, 0 failed, 73 skipped (manual-only)

Fixed by switching every affected goto to path form; see the repair manifest below. Re-running afterward surfaced three more real locator bugs, also fixed (same table).

CMS

Add User: role field isn't the <select> the test expects

Adduser.spec.ts

The Role control is a styled custom dropdown, not a native <select>. The test waited 30s for an element that was never going to appear and timed out before Save was ever clicked — no user was actually created, so no data cleanup needed. Fixed by targeting the real dropdown.

CMS

Delete User depends on Add User having run first

deleteuser.spec.ts

Run alone, the search returns "No data available" and the test fails — it's deleting a user that Add User was supposed to create moments earlier. Tests should set up their own fixtures rather than relying on suite order.

Content

Aircraft Charter categories don't match the spec

Home → Aircraft Charter tab
Qase doc says Passenger, Light Jets, Mid‑size Jet, Heavy Jet, Helicopter, VIP/Executive Airliner
Live app shows Passenger, Air Ambulance, Medical Evacuation, Cargo Charter, Air Survey

Only "Passenger" overlaps. Needs a product call on which list is current before anyone rewrites the test case.

Content

Promo banner copy in the test doc isn't on the page

Home → promo carousel

"READY FOR ADVENTURE" doesn't appear anywhere in the current carousel; the live banner is CMS-managed content that has since changed. Likely a stale test case rather than a bug.

Fixed

Three ambiguous locators, now resolved

DataPemesan · MyHotelBooking

All three were false negatives — the pages worked; the selectors didn't. getByRole('button', {name:'Hotel'}) also matched "My Hotel Booking"; a "not redirected to login" check matched the Contact form's own Email field, which happens to share the placeholder text "Input email address"; a modal check matched both the dialog and its own title text. All three now use an unambiguous locator.
